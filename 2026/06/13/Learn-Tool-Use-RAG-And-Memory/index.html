Learn Tool Use, RAG, And Memory

做检索增强生成：chunk、embed、retrieve、answer with citations

检索增强生成（RAG, Retrieval-Augmented Generation）是目前工业界解决大模型“幻觉”和知识滞后的标准方案。简单来说，它就是给 LLM 配上了一个可搜索的“外挂大脑”。

我们可以将 RAG 拆解为两个阶段：离线索引阶段（Ingestion） 和 在线检索/生成阶段（Inference）。

第一阶段：离线索引 (Building the Brain)

这一步是将你的私有知识库转换为机器可理解的“向量数据库”。

Chunk (切片)

核心逻辑： LLM 的上下文窗口有限，且无关信息会干扰推理，因此必须将长文档切割成具有语义独立性的片段。

  • 策略：
    • 固定窗口切分 (Fixed-size Chunking)： 最简单，例如每 500 个 token 切一段，通常带 10%-20% 的重叠（Overlap），防止切断语义。
    • 语义切分 (Semantic Chunking)： 基于段落、标题、句子进行切分，保证切出来的块是一段完整的话。
  • Go 实践建议： 不要自己写正则，使用 LangChainGo等库中的 RecursiveCharacterTextSplitter。
Embed (向量化)

核心逻辑： 将文本片段（Chunk）转换为高维浮点数数组（向量）。相似的语义在向量空间中距离更近（Cosine Similarity）。

  • 操作： 调用 Embedding 模型（阿里、字节都有）。
  • 存储： 将向量存入向量数据库（Vector DB），如 Milvus、Qdrant、Chroma 或 pgvector。
  • 关键点： 必须保存每个向量对应的 原始文本 和 Metadata（如文件名、页码、段落 ID），这是后续“生成引用”的唯一线索。

第二阶段：在线流程 (Querying & Reasoning)

当用户提问时，RAG 引擎启动工作。

Retrieve (检索)

核心逻辑： 将用户的问题转化为向量，去 Vector DB 中匹配“最相似”的 Top-K 片段。

  • 数学本质： 向量空间的余弦相似度计算。
  • 进阶技巧（工程必选）：
    • 混合检索 (Hybrid Search)： 向量搜索（语义）+ BM25/关键词搜索（专有名词）。
    • Rerank (重排)： 检索到 50 个候选块后，用专门的“重排模型”（如 BGE-Reranker）精挑细选最相关的 5-10 个。这能显著提升准确率。
Answer with Citations (带引用的生成)

这是 RAG 的最后一步，也是考验 Agent 严谨性的地方。为了实现“带引用”，你需要修改 System Prompt 的逻辑。

把搜索、数据库、文件、浏览器、代码执行接成工具

把搜索、数据库、文件、浏览器、代码执行这五大核心能力接入你的 Go 语言 Agent 系统，你就相当于在本地 Windows 上打造出了一个全能型的“AI 权限怪兽”（类似于 Claude Code 或高级运维 Agent 的雏形）。

在工程落地中，接工具的秘诀在于：将复杂的外部底层操作，在 Go 语言中封装成输入简单、输出明确（最好都是 string）的干净函数。

代码执行工具 (Code Execution)

工程逻辑： 让 Agent 拥有在本地 Windows 的 cmd 或 PowerShell 中执行任意命令的能力（这是开发自动化体感最强的部分）。

用到的是 Go 原生的 os/exec 包

浏览器自动化工具 (Browser Use)

工程逻辑： 很多数据没有 API 接口，需要 Agent 像人类一样打开 Chrome、点击网页、抓取 HTML 进行分析

推荐开源库： github.com/chromedp/chromedp（纯 Go 实现的无头浏览器 Chrome DevTools Protocol 库，不需要依赖 Selenium 或 Webdriver）(其实也可以用Playwright‑Go，那个比较全面，但是考虑轻量化还是用chromedp)

数据库操作工具 (Database Internals)

工程逻辑：出于安全考虑，绝不能让大模型直接用 SQL 驱动连接。安全的做法是让 Agent 决定执行某些特定的查询，或者让它输出标准 SQL，由 Go 代码扮演只读（Read-Only）沙箱进行执行。

标准库： database/sql + 对应的驱动（如 github.com/go-sql-driver/mysql）

文件系统 IO 工具 (File System)

工程逻辑： 高级 Agent 需要四个原子能力：读文件、写文件、追加文件、列出目录。将所有读写限制在一个专用的沙箱目录内（如 C:\agent_sandbox\），防止大模型通过传入 ../../Windows/System32 发生路径穿越攻击

标准库： Go 原生 os 包.

网络搜索工具 (Search Engine)

工程逻辑： 补充 Agent 的实时获取时效信息能力。

推荐 API： 工业界目前最喜欢给 Agent 配备的搜索引擎 API 是 Tavily Search（专门为 LLM 优化过，返回的不是繁杂的网页，而是干净的段落摘要）或者 SerpAPI、Google Custom Search。

区分短期上下文、会话记忆、长期记忆

在大模型（LLM）与智能体（Agent）的开发中，记忆（Memory）是决定系统能否展现出“连续性”和“高情商/高智商”的核心。很多初学者容易把它们混为一谈，但从底层工程实现来看，它们的生命周期、存储介质和技术原理截然不同。

维度 短期上下文 (Short-term Context) 会话记忆 (Session Memory) 长期记忆 (Long-term Memory)
人类类比 你的眼睛当前正在看的这一页书 你和朋友这一下午聊天的上下文 你这辈子学过的专业知识和人生经历
生命周期 瞬时（单次 API 请求完成即销毁） 中期（通常指一次连续对话，如数小时内） 永久（跨越数月、数年，跨越不同会话）
Go 存储介质 内存中的 historyMessages 切片 (Slice) Redis / SQLite / 关系型数据库 向量数据库 (Vector DB) 或图数据库
核心技术 Token 窗口拼接 基于 SessionID 的数据库读写与滑动窗口 Embedding 向量检索 (RAG)

短期上下文 (Short-term Context)

  • 本质： 这是大模型当下这一秒钟输入框里能塞进的所有 Token。
  • 工程现状： LLM 是无状态的，你每次请求发送的 Messages 数组就是它的短期上下文。它的上限由模型的 Context Window（如 128k tokens）死死卡住。
  • 致命痛点： 1. 遗忘： 只要当前的 Go 进程关闭，或者你新开一个全新的请求不带历史记录，它就完全不知道你是谁。 2. 价格： 随着聊天越来越长，切片里的 Token 越来越多，单次请求的成本会呈指数级上升。

会话记忆 (Session Memory)

  • 本质： 维系“多轮对话连续性”的机制。让用户在今天下午的对话中，说“它”、“刚才那个”时，模型能心领神会。
  • Go 工程如何落地： 当用户量变大、或者你需要做持久化时，你不能只用内存 Slice。你需要通过前端传来的 SessionID（会话ID），去 Redis 或数据库里捞出该用户最近的 20 条对话记录，拼装成 historyMessages 丢给大模型。
  • 高级调优（滑动窗口/摘要）： 由于短期上下文的限制，当会话聊到第 100 轮时，直接全部发送会爆 Token。Go 代码层需要做“记忆截断”：
    • 滚动窗口 (Buffer Window)： 永远只取最新的 N 条消息。
    • 摘要记忆 (Summary Memory)： 让大模型每隔 10 轮，把前 10 轮的聊天内容压缩成一段 200 字的“前情提要”，作为 System Prompt 锁死在最开头，然后清空旧消息。

长期记忆 (Long-term Memory)

  • 本质： 跨越会话的“人格与常识资产”。即使过了半年，用户开启了一个全新的会话，Agent 依然记得：“这个用户是 xxxxx，喜欢用 Go 语言写 Agent，他的 Windows 电脑上有一个 agent_test_log.txt 文件。”
  • Go 工程如何落地： 长期记忆绝对不能盲目地直接塞进 historyMessages 里。它必须通过 RAG（检索增强生成） 的链路来驱动：
    1. 记忆写入： 当用户在聊天中透露出关键个人特征或重要知识时，Agent 触发工具（如 save_memory），将这段话通过 Embedding 模型转化为向量，存入向量数据库（如 Qdrant / Milvus），并打上 user_id 标签。
    2. 记忆提取： 半年后，用户问：“帮我写个脚本排查我电脑上的日志错误”。Go 代码在把问题发给模型前，先拿这个问题去向量数据库里做一次语义检索，捞出半年前存的记忆：“用户本地有 agent_test_log.txt 运维日志”。
    3. 记忆注入： 把捞出来的长期记忆作为 Context 动态织入当前的短期上下文中。

处理工具失败、空结果、重复调用、幻觉引用

在智能体（Agent）从“玩具”迈向“工业级生产线”的过程中，处理各种异常边界情况（边缘案例，Edge Cases）才是最考验架构师工程内功的地方。

大模型本身具有概率性和不可控性，因此我们在写 Go 代码（智能体宿主程序）时，必须秉持“零信任（Zero Trust）模型”——把大模型当成一个随时可能犯错、说谎、甚至陷入死循环的“叛逆员工”，并在外部用硬编码筑起坚固的护栏。

工具执行失败 (Tool Failures)

比如 Agent 决定调用 read_file 去读一个没有权限的文件，或者网络抖动导致搜索 API 报错。如果你的 Go 代码直接崩溃（Panic）或者返回一个空字符串，大模型就会因为拿不到反馈而发生“逻辑断流”，开始胡言乱语。

采用的解决思路是：“错误即 Observation”机制。不要在 Go 层拦截或消化错误，而是要把错误信息格式化成环境反馈，原封不动地砸回给大模型。

工具返回空结果 (Empty Results)

比如 Agent 调用 search 搜一个极其冷门的技术词，或者执行 db_query 查一张空表，API 成功返回了，但内容是空的（"" 或 []）。大模型看到空结果后，往往会误以为是系统故障，或者在下一轮盲目地陷入复读机状态。

架构解法： “显式状态宣告”。在 Go 语言层进行拦截，绝不给大模型传递真空数据，而是明确宣告“查到了，但是没数据”

工具重复调用与死循环 (Infinite Loop / Repetitive Calling)

当大模型在 Think 阶段钻了牛角尖，或者工具持续报错时，它会陷入死循环：“报错 -> 重试 -> 再报错 -> 再重试”。 API 账单会在几分钟内被刷爆。

架构解法： “状态机双重限流阀”。

  1. 全局最大步数锁（Max Steps Window）。
  2. 同名工具哈希计数器（Repetition Guard）。

幻觉引用 (Hallucinated Citations in RAG)

在做检索增强生成（RAG）时，你给大模型注入了 3 个参考片段：[Source 1]、[Source 2]。但大模型在组织最终人类语言时，由于参数直觉，莫名其妙在陈述句后面标了一个根本不存在的 [Source 5] 或者 [Source 9]，这就叫幻觉引用（乱打标签）。

架构解法： “像素级后置编译器清洗（Post-Processing Filter）”。不要指望在 Prompt 里把大模型教育得多么听话，直接在 Go 代码层面用正则表达式把最终的文本像“编译器”一样过一遍。

让 agent 在回答里给出来源或证据

要让 Agent 在回答里给出极其严谨的“来源或证据”，不能只指望在提示词里对大模型说“请带上来源”。最稳健的工业级做法是：将检索到的资料进行“强编号”，并在模型生成阶段采用“两段式断言约束”或“后置元数据映射”。
