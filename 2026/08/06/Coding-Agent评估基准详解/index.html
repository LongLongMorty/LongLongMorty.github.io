Coding Agent 评估基准详解：SWE-bench、Terminal-Bench 与 τ-bench

开发自己的 Coding Agent 时，最核心的问题莫过于：它到底行不行？

靠人工一个个试任务显然不科学。业界已经沉淀出几套公认的评估基准，从不同维度回答”Agent 行不行”。本文以一问一答的形式，逐一拆解三大主流基准的验证机制、评估指标，以及如何借鉴它们为自研 Agent 搭一套精简评测。

Q1：为什么要用评估基准来检验 Coding Agent？

因为”感觉能用”和”真的能用”是两回事。没有量化标准，你无法回答：

  • Agent 的这次迭代到底是变强了还是变弱了？
  • 是 Prompt 的问题、工具调用的问题，还是模型本身的问题？
  • 它能不能达到可交付、可商用的标准？

评估基准就是一套标准化的”考卷”：给定任务 → 让 Agent 独立完成 → 用客观规则自动判定对错。业界主流的考卷有三套，各考各的能力：

基准 考什么
SWE-bench Verified 能不能读懂 Issue、修好真实 GitHub 仓库的 Bug
Terminal-Bench 2.0 能不能在真实 Linux 终端里自主完成多步骤系统级任务
τ-bench（Sierra） 能不能与真实用户多轮沟通，并在遵守业务规则的前提下操作 API

Q2：SWE-bench Verified 是怎么验证的？

答：核心机制是”真实代码库上下文 + 真实 Issue 说明 → AI 生成 Git Patch → 沙箱运行单元测试”。

它由 OpenAI 与 SWE-bench 原团队（普林斯顿大学等）合作推出，对原始 2,294 个样本进行人工标注与筛选，剔除了描述模糊、测试过苛、环境失效三类噪点，最终精选出 500 个高质量 Python Issue。

验证流程分 4 个阶段：

阶段 1：上下文输入（Input）

给 Agent 提供三样东西：

  • 问题描述（problem_statement）：真实 GitHub Issue 的标题与正文
  • 代码库与 Commit：基于基础 Commit（base_commit）签出的完整代码仓库
  • 提示信息（可选）：Issue 提交之前的讨论评论（hints_text）

阶段 2：生成解决方案（Patch Output）

Agent 对代码库进行搜索、阅读、定位、修改，最终输出一个统一的 Git Patch（Diff 格式） 文件。

阶段 3：隔离环境执行（Evaluation）

用 Docker 容器搭建独立环境，将 Patch 应用到仓库基础版本，然后运行两组单元测试：

测试集 含义 判定要求
FAIL_TO_PASS 对应 Issue 新增/修改的测试，未打补丁前必须失败（即重现 Bug） 打补丁后必须全部通过
PASS_TO_PASS 原有的无关测试 打补丁后必须依然通过（没有破坏已有功能）

Q3：SWE-bench Verified 的评估指标是什么？

答：采用二元判定（Pass/Fail），没有部分得分。

核心指标：解决率（Resolved Rate / Pass@1）

单个样本被判定为 Resolved，必须同时满足三个条件：

  1. Patch 可以被 git apply 成功应用，不产生冲突
  2. 所有 FAIL_TO_PASS 测试全部通过
  3. 所有 PASS_TO_PASS 测试全部通过

只要有一个关联测试失败，该样本就是 0 分。

辅助分析维度（常用于性能与成本诊断）：

  • 成功率 vs API 成本 / Token 消耗：解决一个问题调用模型的次数和花费
  • Patch 大小：过大的 Patch 容易包含噪音或非法改动
  • 运行耗时：从推理到环境构建、运行测试的总用时（单个样本通常设超时上限，如 1800 秒）

Q4：Terminal-Bench 2.0 是怎么验证的？

答：核心机制是”Docker 容器隔离 + 交互式 Agent + 隐藏验证器（Verifier）”。

它由 Laude Institute 等团队推出，包含 89 个经人工精心挑选的高难度终端任务（覆盖系统管理、代码编译、网络配置、漏洞修复、数据库处理等）。如果说 SWE-bench 考”改代码”，Terminal-Bench 考的是”在真实 Linux 终端里干活”。

1. 任务设计：每个任务包含四部分——

  • instruction.md：给 Agent 的自然语言任务指令
  • environment/：预先定义好的 Docker 镜像或环境文件
  • tests/：隐藏在外部（Agent 无法查看或篡改）的自动化验证脚本
  • solution/：人类专家给出的标准参考解法

2. 交互式沙箱：用专用评测框架（如 Harbor）启动 Docker 容器，把 Agent 投进 Bash 终端。Agent 可以不断执行命令、查看输出、创建文件、调试报错，交互轮数可达 200 轮。

3. 自动判定：Agent 认为任务完成（或耗尽轮数/超时）后，触发外部隐藏验证器，在容器内执行自动化指令——检查端口是否监听、文件是否存在且内容正确、编译产物能否跑通等。

Q5：Terminal-Bench 2.0 的评估指标是什么？

答：二值化准确率（Binary Pass/Fail），同样是”全对才算过”。

通过条件：隐藏验证器执行完所有测试脚本且全部断言通过。只要有任何一个断言失败、服务未按要求启动、超过轮数/时间限制，直接判 0（Fail），没有中间分数。

辅助分析维度（Agent 行为诊断）：

  • 交互轮数（Turns）：完成任务用了多少次命令交互
  • Token 消耗与成本（Cost USD）：完成任务的经济效率
  • 超时与死循环率（Timeout / Loop Rate）：是否陷入无效卡死或无限循环

Q6：想为自研 Coding Agent 设计类似 Terminal-Bench 的精简方案，大概设计多少条、保留哪些？

答：推荐 20~25 条任务，按 5 大核心类别划分。

标准 Terminal-Bench 2.0 有近 90 个任务，运行成本高、评测耗时长。自研 Agent 迭代更需要评测快速、成本可控、覆盖核心链路的”基准小工具集”。

为什么是 20~25 条？

  • 48 并发 Docker 沙箱下，**510 分钟**跑完全量评测，适合接入 CI/CD 或日常 Regression Test
  • 每对一个任务增加约 4% 准确率，能拉开不同版本 Agent 的差距
  • 足以覆盖终端交互最核心的 5 大能力维度

核心架构保持三要素：

5 大任务类别及分配（共 25 条）：

类别 条数 考察点 推荐任务示例
环境搭建与依赖编译（Setup & Build） 6 能否自主解决环境配置失败、依赖缺失 Python 依赖冲突修复；缺系统库的 C/C++/Go 项目编译；pyenv/nvm 多语言版本切换；docker compose up 启动多容器服务
深入调试与 Bug 修复（Debugging & Diagnosis） 6 “看日志、定位报错、动态修复” 端口占用进程诊断（lsof/netstat/kill）；崩溃日志定位（OOM/空指针）；环境变量缺失配置；网络连通性/防火墙调试
Git 高级版本控制（Git & VCS Ops） 4 复杂 Git 协同操作 Merge Conflict 解决；Rebase/Cherry-pick；Submodule 缺失修复
系统配置与文件处理（CLI Data Processing） 5 Bash 工具链（awk/sed/jq/find/grep） JSON/YAML 批量改写；大规模文件查找与清洗；数据库 Migration/Seed 数据
跨工具与部署自动化（Deploy & Automation） 4 多命令串联成流水线 一键部署脚本（Makefile/Shell）；systemd/nohup/tmux 后台任务；Nginx 反向代理部署

建议砍掉的内容：

  1. CTF / 网络安全破解类：指令弯弯绕绕（逆向、缓冲区溢出），非通用 Coding/DevOps Agent 的核心场景
  2. 极端算法与数学计算任务：交给 HumanEval 这类代码生成基准去测，在 Terminal 测纯算法意义不大
  3. 主观性强、无确定性断言的任务：只留”最终 verify.sh 返回 0/1”的硬指标

三条构建经验：

  1. 验证脚本一定要黑盒化：不要把测试逻辑写进 instruction.md；校验应直接检查系统状态（如 nc -z localhost 8080、pytest 返回码），而不是看 Agent 输出了什么
  2. 防止 Agent 破坏沙箱：限制交互轮数（建议单任务 30~50 轮）与单命令超时（如 60s），防止死循环卡死评测
  3. 保持基准版本稳定（Frozen Set）：选定的任务不要频繁改动，才能客观衡量迭代中 Prompt、Tool Call 和 Base Model 的能力变化

Q7：τ-bench（Sierra）呢？

答：它考的是”与真实用户多轮沟通 + 遵守业务规则 + 操作 API 完成业务任务”，主打企业级商用场景。

τ-bench（Tool-Agent-User Interaction Benchmark）由 Sierra 团队（Bret Taylor 与 Clay Bavor 创立的 AI 独角兽）推出。传统基准大多是”用户一次性给出长 Prompt，Agent 自己执行”，但在客服、售前、业务办理场景中会失效：

  1. 信息不完整：用户不会一次说完所有参数，Agent 必须多轮提问去收集
  2. 业务规则限制（Policy）：如”未二次确认不得扣款”，Agent 必须严格遵守
  3. 用户行为随机：可能中途改主意、给错信息、表达模糊

核心架构：采用 POMDP 建模，三个角色——

  • Environment：真实业务场景（τ-retail 电商、τ-airline 航空），预置数据表与工具 API（cancel_order、rebook_flight）
  • Policy Document：详细的业务规则文档
  • User Simulator：LLM 扮演用户，带着特定意图，但不主动说出条件，等 Agent 来问

评估指标：

  • 状态判分法（Stateful Evaluation）：不看对话说得漂不漂亮，只看最终数据库状态是否与 Ground Truth 一致。允许对话过程有随机性，只要最终 API 决策正确
  • $pass^k$ 连续成功率：传统 $pass@k$ 是”k 次中有 1 次成功就算过”（衡量上限）；τ-bench 要求 k 次连续全部成功（k=8）才算过（衡量可靠性）。企业部署无法容忍”试 8 次有一次能对”

演进版本：

  • τ²-bench：双控协作（Dual-Control），Agent 不能远程操作，必须指导用户在手机上实操并引导排查
  • τ³-bench：扩展到语音交互、知识库联动等更复杂场景

Q8：三个基准怎么选？

答：看你的 Agent 是干什么的。

维度 SWE-bench Verified Terminal-Bench 2.0 τ-bench (τ²/τ³)
主攻场景 GitHub 仓库代码修改与 Bug 修复 Linux 终端系统配置、编译与运维 真实业务客服/助理、多轮人机协同
关键考验 长上下文代码理解与重构 多步骤命令行交互与报错调试 多轮信息搜集、Policy 遵守、API 操作
交互对象 静态代码库（代码 Patch） Linux Shell 交互环境 LLM 模拟用户 + 业务 API 数据库
判定标准 pytest 单元测试全通过 外部隐藏测试脚本全通过 最终数据库状态断言
评价特色 端到端代码解决率 系统多步链条鲁棒性 $pass^k$ 连续成功率（商用指标）

选型建议：

  • 开发代码修复类 Agent → 参考 SWE-bench Verified 的思路（Patch + FAIL_TO_PASS/PASS_TO_PASS）
  • 开发DevOps/终端操作类 Agent → 参考 Terminal-Bench 2.0 的思路，按 Q6 的方案裁剪出 20~25 条快速评测集
  • 开发垂直领域业务智能体、Copilot 或多轮客服 Agent → 参考 τ-bench 的设计思路（规则 Policy + API 沙箱 + 模拟用户 + 数据库状态判定），这是目前工业界最值得参考的标准框架

一句话总结：SWE-bench 考改代码，Terminal-Bench 考终端干活，τ-bench 考业务对话。评估基准不是越全越好，挑一个贴合你 Agent 场景的，先跑起来，再慢慢加任务。
