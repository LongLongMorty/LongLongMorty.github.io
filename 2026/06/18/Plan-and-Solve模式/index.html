Plan-and-Solve模式

在我们掌握了 ReAct 这种反应式的、步进决策的智能体范式后，接下来将探讨一种风格迥异但同样强大的方法，Plan-and-Solve。顾名思义，这种范式将任务处理明确地分为两个阶段：先规划 (Plan)，后执行 (Solve)。

如果说 ReAct 像一个经验丰富的侦探，根据现场的蛛丝马迹（Observation）一步步推理，随时调整自己的调查方向；那么 Plan-and-Solve 则更像一位建筑师，在动工之前必须先绘制出完整的蓝图（Plan），然后严格按照蓝图来施工（Solve）。事实上我们现在用的很多大模型工具的Agent模式都融入了这种设计模式。

维度 ReAct 模式 (边想边做) Plan-and-Solve 模式 (先谋后动)
核心思想 Thought -> Action -> Observation 循环。走一步看一步，根据工具返回的结果决定下一步做什么。 Plan -> Solve (Sub-tasks)。先生成全局路线图，然后按部就班地把每个子任务消灭。
思维方式 动态调整、应变能力强、深度依赖即时反馈。 结构化、条理清晰、顾全大局，不容易跑偏。
适用场景 探索性任务、需要频繁和环境交互（如查数据库、实时搜索、调 API）。 复杂的长文本创作、多步骤的数学/逻辑推理、目标明确的流水线任务。
缺点 容易陷入死循环（Looping），或者走着走着“忘了初衷”（Goal Drift）。 如果初始计划有误，而执行中没有微调机制，可能会“一条道走到黑”。

规划阶段

规划阶段的核心目标是“去模糊化”。大模型直接面对复杂任务时容易顾此失彼，Planner 的任务就是通过 Prompt Engineering，逼迫 LLM 输出一个结构化的任务列表。

在实际工程中，我们通常让 Planner 返回 JSON 数组，这样 Go 语言就能轻松地将其解析为切片（Slice）。

执行器与状态管理（Executor & State Manager）

这两个部分在运行时是紧密交织的。

  • 状态管理器：维护一个“全局黑板”。执行器每做完一步，就把结果写到黑板上。
  • 执行器：每开始新的一步，先去黑板上读一读之前的上下文（Context），确保自己拥有最新的“记忆”，然后开始执行。

有了这两个组件后，你的主程序逻辑会变得异常清晰和健壮。可以轻松地在步骤之间加入日志、错误重试、甚至人工审批（Human-in-the-loop）。

Reflection 机制

智能体一旦完成了任务，其工作流程便告结束。然而，它们生成的初始答案，无论是行动轨迹还是最终结果，都可能存在谬误或有待改进之处。Reflection 机制的核心思想，正是为智能体引入一种事后（post-hoc）的自我校正循环，使其能够像人类一样，审视自己的工作，发现不足，并进行迭代优化。

  • 单步反思：每一步执行完，反思当前输出是否合格、有无缺失、偏离目标
  • 全局反思：全部步骤跑完后，复盘整套流程，判断整体结果是否满足总任务
  • 重规划 / 重试：反思发现缺陷后，可重新生成子任务、重新执行失败步骤、补充遗漏步骤

尽管 Reflection 机制在提升任务解决质量上表现出色，但这种能力的获得并非没有代价。在实际应用中，我们需要权衡其带来的收益与相应的成本。尽管 Reflection 机制在提升任务解决质量上表现出色，但这种能力的获得并非没有代价。在实际应用中，我们需要权衡其带来的收益与相应的成本。此外，Reflection 是一个串行过程，每一轮的优化都必须等待上一轮的反思完成。这使得任务的总耗时显著延长，不适合对实时性要求高的场景。
