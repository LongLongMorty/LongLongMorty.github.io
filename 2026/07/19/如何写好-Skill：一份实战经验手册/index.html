一、先搞清楚 Skill 是什么

1.1 Skill 到底是啥

说白了，Skill 就是给 AI 编程助手（Claude Code、CodeBuddy 等）”加装”的能力包。本质上，它是一种结构化的 Prompt Engineering——通过标准的文件格式，把分散在人脑中的领域知识、操作流程和最佳实践，转化为 AI 可理解、可执行的指令集。

物理上看，它就是一个文件夹，里面放一个 SKILL.md 文件，再加上一些可选的脚本和参考资料。核心就三样东西：

  • 指令（Instructions）：告诉 AI 该怎么干活，按什么步骤来
  • 上下文（Context）：给 AI 补课，告诉它你的项目背景、团队规范这些它不可能凭空知道的东西
  • 工具（Tools）：一些辅助脚本、配置模板，AI 可以直接拿来用

打个比方：裸着的 AI 就像一个刚入职的新人，啥都得问；装了 Skill 之后，就像拿到了老员工整理的操作手册，照着就能干。

1.2 为什么要写 Skill

痛点 实际表现 Skill 怎么解决
知识太散 经验藏在 TAPD、Wiki、代码注释、甚至某个人的脑子里 全部整理进 Skill，将知识结构化封装为标准技能包
重复搬砖 同样的活反复干，每次都要手动来一遍 写成 Skill 让 AI 自动跑
做出来的东西不统一 张三做一个样，李四做另一个样 用 Skill 固定流程，谁来做都一个标准
新人上手慢 来个新人得教半天，对方还不一定记得住 Skill 本身就是最好的培训材料
人走知识也走 核心成员一离职，很多”部落知识”就没了 把经验沉淀进 Skill，知识完整留存

1.3 Skill 怎么运作的

Anthropic 设计了一个”渐进式加载”机制，分成三层：

层级 加载时机 内容要求 Token 成本参考
Level 1 常驻（每次对话都在） name + description，控制在 100 字以内 约 50-150 Token / 个 Skill
Level 2 匹配触发时一次性加载 SKILL.md 正文，建议不超过 500 行 约 2,000-5,000 Token
Level 3 执行中按需读取 脚本、参考文档、模板等 按实际引用大小计算

为什么要关注 Token 成本？因为 Skill 不是免费的——每加载一个 Skill 都会占用上下文窗口。假设你装了 20 个 Skill，光 Level 1 就要吃掉 1,000-3,000 Token；如果 AI 一次触发了 2 个 Skill，Level 2 又要再加 4,000-10,000 Token。上下文越满，AI 的注意力越分散，回答质量反而可能下降。

核心原则：Level 1 越精准越好（决定触发时机），Level 2 越精简越好（减少 Token 消耗），Level 3 放心放（按需加载不占常驻空间）。

Skill 的触发模式：

触发模式 说明 典型场景
自动触发 AI 根据 description 语义匹配，自动决定是否加载 用户正常提问，AI 判断相关则触发
手动触发 用户主动通过命令（如 /skill xxx）指定使用 需要精确控制使用哪个 Skill 时
规则触发 基于文件类型、目录、特定操作等条件自动触发 打开 .go 文件时自动加载 Go 相关 Skill

1.4 Skill 能用在哪些场景

场景 比如说……
代码迁移/改造 框架升级、换 API、架构重构这些
代码审查 按团队规范自动跑一遍 Review，直接出报告
写文档 按固定格式生成 API 文档、使用说明等
项目初始化 按团队模板一键搭好项目骨架、配好 CI/CD
自动化测试 根据接口定义自动生成测试用例
数据处理 数据库变更、Excel 分析、日志解析这些体力活

3.1 Description 写好了，一切就成功了一半

Description 太重要了。AI 就是靠它来判断”用户现在说的这个事，该不该用这个 Skill”。

实用技巧：”触发评估”——你可以自己想 20 个问题（一半该触发、一半不该触发），然后测试一下 AI 是不是每次都能正确判断。

3.2 开头就说清楚：做什么、为什么、要不要做

别让 AI 猜你的意图。每个 Skill 上来就该把三件事说明白：做什么、为什么、怎么判断是否需要做。

要点：

  1. 把起点和终点说清楚——从哪迁到哪，别含糊
  2. 告诉 AI 什么时候不用做——给个前置检查条件，及时跳过
  3. 给出具体的检查命令，而非模糊描述

3.3 用祈使句下指令，解释”为什么”

第一，别用商量的口吻，直接说”做什么”

第二，与其一堆”MUST”，不如讲清楚为什么

AI 要是理解了背后的道理，遇到你没想到的情况也能做出合理判断。

3.4 给出”改之前 vs 改之后”的对比

这是 Skill 中最关键的部分——让 AI 清楚知道”改什么”和”改成什么”。

方式一：注释标注（适合简单变更）

方式二：完整文件对比（适合复杂变更）

方式三：Diff 格式（推荐，最直观）

3.5 Few-Shot，多给几个例子，AI 就不会瞎发挥

在 Skill 里放 3-5 个高质量的输入/输出示例，AI 的表现会稳定很多。光靠文字描述，AI 可能理解偏了；但给了具体的示例，它就知道”哦，原来你要的是这个效果”。

关键原则：

  • 覆盖典型场景：正常情况、边界情况、错误情况各来一个
  • 输入输出成对出现：每个示例都要有”给什么”和”出什么”
  • 示例之间有差异：别搞 3 个长得差不多的，要能展示不同的处理分支
  • 先放最典型的：AI 会更倾向于模仿前面的示例，把最常见的场景放第一个

3.6 善用可视化：决策树与流程图

复杂流程光靠文字描述，不管是人还是 AI 都容易看晕。用表格或者流程图把不同情况列出来，AI 就不容易搞混。

四、Skill 太长了怎么办——拆（模块化）

4.1 什么时候该拆

  • 文件写着写着超过 500 行了（Anthropic 建议的上限）
  • 包含多个可独立的工作流程
  • 有些步骤可以单独用，没必要每次都把整个 Skill 跑一遍
  • 不同部分改动频率差很多

4.2 拆成什么样——模块化设计

复杂场景：拆成主 Skill + 子 Skill

4.3 拆分的几个原则

  1. 一个子 Skill 只管一件事（单一职责）
  2. 把依赖关系写明白——子 Skill 之间有先后顺序的，在文档里写清楚
  3. 每个子 Skill 都能单独使用——拆出来的子 Skill 不应该离了主流程就没法跑

五、一些进阶的写法

5.1 能用表格就用表格

AI 读表格比读大段文字准确得多。能结构化的信息，尽量用表格呈现。

5.2 复杂检查逻辑？写成脚本

如果前置检查或配置流程比较复杂，别全堆在 SKILL.md 里，写成脚本放到 scripts/ 目录下，SKILL.md 里直接调用。

5.3 提供多种方案适配不同场景

同样的目标，不同项目的结构可能完全不一样。多准备几种方案，让 AI 根据实际情况选合适的：

  • 方案 A：集中式请求封装（推荐）——适用于项目有统一请求工具函数
  • 方案 B：分散式直接调用——适用于各模块直接引用旧包，无统一封装
  • 方案 C：渐进式迁移——适用于大型项目，无法一次性完成迁移

5.4 把容易踩的坑标出来

AI 也会犯错，特别是一些人类凭经验才能避开的坑。在 Skill 里显眼地标出来，能省很多事。

5.5 FAQ 不是摆设

写得好的 FAQ 能帮 AI 处理那些”说不清道不明”的边界情况。

六、要调外部服务？MCP vs HTTP

6.1 它们的区别在哪

维度 MCP 调用 HTTP/API 直接调用
本质定位 AI Agent 的标准化工具协议，专为 LLM 设计 通用网络通信协议
传输方式 JSON-RPC 2.0 over stdio / SSE HTTP/HTTPS REST/GraphQL
上下文感知 原生支持流式传输和 AI 对话上下文 无状态 Request-Response
调用方式 AI 自动识别并调用已注册的 MCP 工具 需在脚本中手动编写请求代码
鉴权管理 MCP Server 统一管理 每个脚本自行处理 Token/Key
跨平台复用 一次注册，多平台均可调用 绑定特定脚本语言和运行环境

6.2 怎么选

MCP 管连接，Skill 管流程，HTTP 脚本兜底处理 MCP 顾不上的场景。

七、安全意识：别让 Skill 变成漏洞入口

7.1 绝不硬编码敏感信息

永远通过环境变量或配置文件（加入 .gitignore） 来管理。

7.2 危险操作必须加确认

7.3 数据库操作先备份再改

7.4 防范 Prompt 注入

核心原则：区分”指令”和”数据”。Skill 中的步骤是指令，从外部读取的内容是数据。数据永远不应该被当成指令来执行。

7.5 安全检查清单

  • 文件中没有硬编码的密钥、密码、Token
  • 危险操作（删除、覆盖、DDL）有确认或备份机制
  • 脚本中的用户输入做了校验，不会被注入
  • 文件路径操作没有使用未经验证的变量拼接
  • 网络请求使用了 HTTPS，并设置了合理的超时

触发评估：解决的是”Description 写得好不好”这个问题。自动生成正例和反例，批量测试触发准确率。

效果评估：准备一批有评分标准的测试用例，让 Skill 实际跑一遍再自动打分。

评估达标的参考标准：

指标 达标线 优秀线
触发准确率（Precision） ≥ 85% ≥ 95%
触发召回率（Recall） ≥ 85% ≥ 95%
效果通过率 ≥ 80% ≥ 90%
相对提升率 ≥ 30% ≥ 50%

小贴士：如果 Skill 是团队共享的，建议在 PR Review 时要求附带评估报告。就像代码变更要跑单测一样，Skill 变更也应该跑评估——这就是”Skill 的单元测试”。

9.3 评估 Skill 好不好用

Anthropic 推荐了一套评估方法：

  1. 准备测试用例——正常情况和边界情况都要有
  2. 对比跑一下——有 Skill 和没 Skill 各跑一遍
  3. 定义通过标准——每个用例怎么算”通过”
  4. 看数据——通过率、Token 消耗、运行时间
  5. 根据结果调整——哪里不行改哪里，再跑一轮

十、Skill 跑不通？调试与排错指南

常见排查流程

经验之谈：大多数问题（估计 70% 以上）出在前两步——要么 Skill 没加载成功，要么 Description 写得不够好导致没触发。

多个 Skill 冲突了怎么办

策略 做法 适用场景
差异化 description 让每个 Skill 的 description 有明确的区分关键词 功能有部分重叠的 Skill
合并为一个 如果两个 Skill 经常一起被触发，考虑合并 高度相关的 Skill
添加排斥说明 显式说明”本 Skill 不处理 XXX 场景” 容易被误触发的 Skill
手动指定 在对话中明确指定使用哪个 Skill 需要精确控制时

十一、Skill 的生命周期管理

版本控制

变更类型 版本变化 示例
修复问题、补充说明 1.0 → 1.1 修复某个边界场景的处理逻辑
新增步骤或场景 1.1 → 1.2 增加对 gRPC 客户端的支持
重大结构调整 1.x → 2.0 从单体拆分为模块化架构

团队协作

  • 像代码一样 Review——新 Skill 或重大修改通过 PR 提交
  • 维护变更日志——在 Skill 目录下维护 CHANGELOG
  • 避免冲突——按功能模块分工，各写各的子 Skill
  • 定期清理——不再使用的 Skill 及时归档或删除

持续迭代

Skill 不是写完就不管了。用的过程中肯定会发现问题，定期打磨一下：

  • 记下来哪里出过问题
  • 找找规律——同一类错误反复出现？那就是 Skill 写得不够清楚
  • 从个案中提炼通用规则
  • 越精简越好

十二、别踩这些坑——常见反模式

反模式 一句话症状 解法指引
大杂烩 Skill 一个 Skill 干三件事 拆分（第四章）
Description 黑话 全是内部术语 用通用语言 + 技术关键词（3.1 节）
没有示例 纯文字描述 加 Few-Shot（3.4、3.5 节）
没有验证点 做完才检查 关键步骤加检查点（9.1 节）
写死数值 硬编码配置 给判断规则和参考范围
当 Wiki 写 背景 300 行正文 50 行 背景放 references/（5.2 节）

十三、总结：写好 Skill 的核心检查清单

写的内容对不对

  • 目标明确：做什么、为什么做、什么时候触发
  • Description 精准：AI 能不能在合适的时候自动匹配到
  • 语气直接：直接下指令，而不是绕弯子
  • 讲了为什么：不只是说”必须这样做”，还解释了原因
  • 例子够不够：有没有 3-5 个 Before/After 对比或者示例
  • 场景考虑全了：多种情况都覆盖到了
  • 坑标出来了：容易犯的错误和注意事项是否标注了
  • 能验证：有验证清单和能跑的检查命令

结构合不合理

  • YAML 元数据完整
  • SKILL.md 正文控制在 500 行以内
  • 模块化拆分：超过 500 行的要拆成主 Skill + 子 Skill
  • 依赖明确：清楚声明前置条件和相关 Skill
  • 可视化表达：善用表格、ASCII 流程图

安全过关了吗

  • 无硬编码密钥
  • 危险操作有确认或备份
  • 输入有校验，不会被注入
  • 路径安全（防止路径穿越）
  • 网络请求使用 HTTPS，设置合理超时

附录：核心术语速查

术语 含义
Level 1/2/3 Skill 的三层渐进式加载机制：元数据 → 正文 → 脚本资源
Few-Shot 在 Skill 中提供多个输入/输出示例，让 AI 模仿学习
Before/After 改动前后的代码对比，让 AI 清楚知道”改什么”和”改成什么”
检查点（Checkpoint） 在关键步骤之间插入的验证命令，用于及时发现偏差
Description YAML 头信息中的描述字段，决定 Skill 何时被自动触发
MCP Model Context Protocol，专为 AI 设计的标准化工具协议
主 Skill / 子 Skill 模块化拆分后的编排层和执行层
反模式 常见的”写了但不好使”的模式，应当避免
