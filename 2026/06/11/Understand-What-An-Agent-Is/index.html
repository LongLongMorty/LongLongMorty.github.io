Agent 学习笔记

Stage 0: Understand What An Agent Is

1. 区分 chatbot、workflow、agent、multi-agent

这四个概念代表了大模型（LLM）应用落地中从简单到复杂、从被动到主动的演进路径。我们可以从核心定义、自主性、控制流等维度来彻底理清它们的区别。

Chatbot（聊天机器人）

  • 核心特征： 纯粹的”一问一答”与状态保持。
  • 如何工作： 用户输入 Prompt，LLM 输出文本。它主要依赖大模型本身的参数知识和上下文理解能力。
  • 自主性： 极低。它完全是被动的，用户不说话，它绝对不行动；用户说一句，它回一句。
  • 控制流： $User \rightarrow LLM \rightarrow User$ 的简单线性循环。
  • 典型场景： 基础版 ChatGPT、纯文本客服、闲聊陪伴。

Workflow（工作流 / 静态编排）

  • 核心特征： 确定性的、流式处理的”流水线”。
  • 如何工作： 开发者在后台把任务拆解成固定的步骤（步骤A $\rightarrow$ 步骤B $\rightarrow$ 条件判断 $\rightarrow$ 步骤C）。大模型在其中通常只扮演某个节点（比如负责”摘要”或”提取关键词”）。
  • 自主性： 低。虽然能处理复杂任务，但它的路线是死板的。它没有决策权，必须严格按照工程师画好的流程图（DAG）走。
  • 控制流： 确定性的硬编码逻辑（如条件分支、循环）。
  • 典型场景： 自动化文章发布（抓取 $\rightarrow$ 翻译 $\rightarrow$ 润色 $\rightarrow$ 排版 $\rightarrow$ 发布）、报表自动生成。

Agent（智能体 / 动态决策）

  • 核心特征： 拥有 思考（Reasoning）、记忆（Memory）和 使用工具（Tools） 的能力。
  • 如何工作： 用户只给一个模糊的目标（例如：”帮我订一张明天去北京最便宜的机票”）。Agent 会自己思考：
    1. 拆解任务（Plan）：我需要先查航班，再对比价格。
    2. 使用工具（Action）：调用外部携程或飞猪的 API。
    3. 观察结果（Observation）：发现某航班最便宜，但时间不好，重新调整策略。
  • 自主性： 高。它有”自主决定下一步做什么”的能力。
  • 控制流： 动态的 $Plan \rightarrow Act \rightarrow Observe$ 循环（如 ReAct 框架）。
  • 典型场景： 个人AI助理、能够自主Debug并修改代码的开发助手。

Multi-Agent（多智能体系统）

  • 核心特征： “群体智能”，通过分工、合作或对抗来解决复杂大任务。
  • 如何工作： 面对一个极度复杂的工程，单个 Agent 可能会因为上下文太长或术业不专攻而”懵圈”。Multi-Agent 把任务分给具有不同 Profile（角色设定）的 Agent。
    • Agent A（产品经理） 负责写需求；
    • Agent B（架构师） 负责设计框架；
    • Agent C（程序员） 负责写代码并向架构师汇报。
  • 自主性： 极高。不仅单个 Agent 有自主性，Agent 之间还能通过通信协议动态交互。
  • 控制流： 复杂的网络化/网格化通信流，包含 SOP（标准作业程序）或自由讨论。
  • 典型场景： 自动化软件团队（如 MetaGPT、ChatDev）、复杂的博弈对抗系统。

总结与横向对比

为了更直观，我们可以用一个”软件开发公司”的例子来打比方：

  • Chatbot 像是公司里的实习生，你问一句话，他翻一下书答一句话，不盲动。
  • Workflow 像是公司的打卡审批系统，流程是死板的，A审批完自动到B，不能走错一步。
  • Agent 像是公司里的全栈高级工程师，你给他一个任务，他自己去查文档、写代码、查Google，最后把结果交给你。
  • Multi-Agent 则是整家软件公司，产品、开发、测试各司其职，甚至能自己开会吵架，最终交付一个复杂的系统。

核心驱动 大模型生成能力 开发者定义的死逻辑 目标驱动+大模型决策 角色分工+协作机制
控制流 线性一问一答 确定性图结构 (DAG) 动态循环 (Loop) 复杂的网状多向通信

2.理解 agent 的基本循环：observe -> think -> act -> observe。

这个循环也被称为 OTA 循环（或者在学术界常说的 Perception-Cognition-Action 闭环）。它是所有具身智能、自动驾驶和 AI Agent 的底层灵魂。

我们可以把 Agent 想象成一个”活在黑盒里、通过传感器和机械臂与外界交互的机器人”。每一次循环，都是它与物理或数字世界进行的一次生命搏击。

下面我们一层层剥开这个循环的本质，并用一个”智能终端 Agent 帮用户排查 Linux 服务器 CPU 飙高”的硬核例子来具象化它。

核心四步的深度拆解

👁️ Observe（观察/感知）

  • 本质： 获取环境的当前状态（State）。Agent 不能闭门造车，它必须通过”眼睛”看世界。
  • 在数字世界中： 观察意味着接收用户的 Prompt、读取 API 的返回结果、捕获终端的 stdout/stderr、或者读取数据库的最新一条记录。
  • 核心难点： 信息过滤。环境信息往往是嘈杂、冗长的，Agent 需要从中提取出对当前任务有用的”特征”。

🧠 Think（思考/决策）

  • 本质： 大模型（LLM）的 核心推理过程。Agent 结合自己的 历史记忆（Memory）、当前观察（Observation） 和 最终目标（Goal），进行逻辑推演。
  • 具体表现形式：
    • Chain-of-Thought (CoT)： “我现在看到了现象 X，根据我的知识库，可能的原因是 Y。我下一步应该去验证 Z。”
    • Planning（规划）： 把大目标拆解成子任务。
  • 核心难点： 幻觉控制与边界判断。想得太多容易陷入死循环，想得太浅容易做出错误决定。

🛠️ Act（行动/执行）

  • 本质： 对环境施加影响，试图改变环境状态。
  • 具体表现形式： Agent 自己其实写不出答案，它必须通过调用工具（Tools / Plugins）来和外界发生物理接触。比如：执行一条 Bash 命令、发送一个 HTTP 请求、调用 SQL 写入数据。
  • 核心难点： 参数组装的准确性。LLM 必须准确输出符合工具 Schema 的 JSON 或文本格式。

🔄 再次 Observe（二次观察与反馈）

  • 本质： 这是 Agent 区别于普通脚本的关键一步！
  • 动作执行完后，环境变了。Agent 再次观察：工具执行成功了吗？报错了吗？离目标更近了还是更远了？
  • 这种反馈机制（Feedback Loop）让 Agent 具备了极其强大的自我纠错（Self-Correction）能力。

经典框架（如 ReAct）中，这四步叫什么？

如果你去看开源的 Agent 框架（如 LangChain, AutoGPT），在它们的 Prompt 模版或日志里，这个循环通常被固化为四个关键词：

  • Thought: Agent 的内心独白（我想做什么）。
  • Action: Agent 决定调用的工具名称（Tool Name）和入参（Arguments）。
  • Observation: 工具执行后返回给大模型的原生数据（工具的输出）。
  • (然后拿着 Observation 再次进入下一个 Thought…)

💡 终极思考

普通的程序是”线性的、一触即溃的”——如果中间某一行命令报错，程序就直接 exit(1) 了。

而基于 Observe-Think-Act 循环的 Agent，本质上是一个”自适应系统”。哪怕 Act 报错了，它在下一轮 Observe 里看到的是一堆 Error Matrix，它的 Think 会告诉它：“哦，刚刚的路走不通，换个命令再试一次”。

这也是为什么在 Agent 的设计中，闭环的反馈质量（Observation）往往比大模型本身的参数量更能决定一个 Agent 的工程上限。

3.什么时候不该用 agent

虽然 Agent 展现出了极强的”自主思考”和”自适应”能力，但在实际工程工程落地中，盲目上 Agent 往往是灾难的开始。

在以下这五种场景下，不仅不该用 Agent，反而应该坚决倒退回 Workflow（工作流）、传统代码（Hard-coded Logic） 甚至纯人工阶段。

流程高度确定、容错率为零的场景

  • 典型特征： 任务有极其严格的业务逻辑或法律合规要求，每一步都必须 $100%$ 精确，不能有任何偏差（如金融结算、医疗诊断、法律合同生成、机票预订扣款）。
  • 为什么不用 Agent： Agent 的底层是 LLM，而 LLM 本质上是概率模型。只要存在概率，Agent 的 Think 阶段就会发生”幻觉”，Act 阶段就可能组装出错误的参数。
  • 替代方案： 使用 Workflow（工作流） 或传统条件判断（if-else）。在关键扣款或合规节点，用确定性的代码死死卡住。

对响应时间（Latency）要求极高的场景

  • 典型特征： 毫秒级（ms）响应的需求。例如高频交易、搜索自动补全、即时游戏交互。
  • 为什么不用 Agent： Agent 的一次完整运转需要经历 Observe -> Think -> Act -> Observe 的循环。这意味着在一个任务中，它可能需要连续多次、串行地请求大模型。大模型生成 Token 本身就很慢，多次串行叠加（加上思考过程中的 CoT 冗长文本），会导致端到端延迟飙升到几秒甚至十几秒。
  • 替代方案： 针对特定任务训练微调小模型（SLM），或者直接使用传统的启发式算法和缓存机制。

成本极其敏感、调用频次巨大的场景

  • 典型特征： 每天有数百万甚至数千万次的并发请求，且单次业务的商业利润极低。
  • 为什么不用 Agent： Agent 为了表现得聪明，通常会在 Prompt 中塞入大量的上下文（历史记忆、工具列表、少样本提示），并且会通过”内心独白（Thought）”产生大量的中间 Token。这种 Token 放大效应 会让你的 API 账单呈指数级增长。
  • 替代方案： 将任务拆解，把非必须由大模型推理的步骤全部用工程代码（如 Python/Go 脚本）固化，只在核心的文本处理节点调用一次单发 LLM。

目标模糊且缺乏明确边界的复杂工程

  • 典型特征： 比如”帮我重构这个拥有 10 万行代码的旧系统”，或者”帮我运营一个科技媒体账号并实现盈利”。
  • 为什么不用 Agent： 当目标过大、环境过于复杂时，Agent 会陷入”无限循环（Infinite Loop）”或“动作退化（Action Degrade）”。它会在 Observe 到错误后不断重试，或者由于上下文窗口（Context Window）被垃圾信息填满而彻底迷失方向，白白烧掉大量 Token 却无法收敛到最终结果。
  • 替代方案： 采用 Multi-Agent 团队机制 进行人工干预下的角色分工，或者由人类工程师将大目标拆解为极小的任务流，再交给 Agent 执行。

工具本身不完善或环境不具备隔离性的场景

  • 典型特征： 比如让 Agent 拥有你个人电脑的最高 root 权限，或者直接去操作生产环境的真实数据库。
  • 为什么不用 Agent： Agent 的 Act 依赖工具。如果工具的破坏力极大（如 rm -rf 或 DROP DATABASE），且没有做沙箱隔离（Sandbox），Agent 一旦在 Think 阶段理解错了一句话，或者受到提示词注入攻击（Prompt Injection），其执行的破坏性动作将是不可逆的。
  • 替代方案： 在 Act 和环境之间强制加入 Human-in-the-Loop（人工确认机制）。Agent 只能生成预执行指令，必须由人类点击”允许”后才能真正落地。

Anthropic: Building effective agents 阅读

Anthropic 于 2024 年底发表的这篇技术博客 《Building effective agents》（构建高效智能体） 已成为 AI 工程界公认的”神作”。它系统的阐述了如何真正把 Agent 落地到生产环境，核心观点是：放弃复杂的 Agent 框架，回归简单、可组合的架构设计。

以下是该长篇技术分享的完整核心内容中文编译版，为你保留了所有硬核的架构图解、设计模式与工程原则：

构建高效 AI 智能体 (Building Effective Agents)

文／Anthropic 团队

在过去一年里，我们与数十个跨行业的团队合作构建了大语言模型（LLM）智能体。我们发现，最成功的落地案例无一例外都使用了简单、可组合的模式，而不是复杂的自动化框架。

本文旨在分享我们在构建智能体过程中的实用指南，涵盖三种核心架构的选择，以及如何设计高质量的工具接口。

一、 核心概念：工作流（Workflows） vs 智能体（Agents）

在开发”智能体系统”时，我们首先要区分两种不同的系统设计：

  • 工作流（Workflows）： 系统通过预定义的代码路径来编排 LLM 和工具。LLM 在这里充当流水线上的某个工人。
  • 智能体（Agents）： LLM 拥有动态控制决定权，它可以根据环境反馈、自主选择工具，在一个循环（Loop）中反复迭代直至目标完成。

核心原则： 如果你能用预定义的工作流（Workflow）解决问题，那就坚决不要使用复杂的智能体（Agent）。因为工作流更加稳定、可预测且易于 Debug。只有在任务充满动态变数、需要高度灵活性时，才选择 Agent。

二、 基础积木：被增强的 LLM (The Augmented LLM)

无论是工作流还是智能体，最基本的构建单元都是一个”被增强的 LLM”。相比于纯文本对话，它被扩充了以下能力：

  • 检索（Retrieval）： 传入相关的上下文数据（如 RAG 系统）。
  • 工具使用（Tools）： 能够调用 API、执行代码、执行数据库读写。

三、 四大核心工作流模式 (Workflow Patterns)

对于那些步骤明确、可以用硬编码固化流程的任务，Anthropic 总结了 4 种最有效的设计模式：

  1. 提示链模式 (Prompt Chaining)

将一个大任务顺序拆解为多个子任务，每个子任务的 LLM 输出作为下一个子任务的输入。

  • 适用场景： 数据清洗、多步骤文本生成。每次处理都有明确的检查点。
  1. 路由模式 (Routing)

利用 LLM 作为”路由器”，根据用户输入的类型，将其分发到专门的下游 Prompt 或子系统。

  • 适用场景： 复杂客服系统、多国语言分流。
  1. 并行模式 (Parallelization)

LLM 可以同时并发处理多个无依赖的子任务。分为两种变体：

  • 投票（Voting）： 多个模型针对同一任务生成输出，通过代码或另一个 LLM 聚合出最佳答案。
  • 分片（Sectioning）： 将大任务拆分成多块并行处理（如同时编写一本书的三个不同章节）。
  • 适用场景： 代码多方案审查、大规模内容并行处理。
  1. 评估器-优化器模式 (Evaluator-Optimizer)

这是生成高质量内容的核心闭环。一个 LLM 负责生成初始内容，另一个 LLM（评估器）负责挑刺并给出修改意见，生成器根据反馈进行迭代。

  • 适用场景： 复杂代码编写、严谨的法律合同草拟、翻译精润。

四、 智能体架构：自适应循环 (Autonomous Agents)

当任务的步骤无法被提前预知，且需要根据中间结果不断调整策略时，就必须引入 Agent（智能体）。

在工程落地中，Agent 最常在以下领域取得成功：

  1. 代码问题修复（Coding Agents）： 运行单元测试 $\rightarrow$ 发现报错 $\rightarrow$ 修改代码 $\rightarrow$ 重新运行测试 $\rightarrow$ 直至全绿通过。
  2. 计算机操作（Computer Use）： 借助屏幕截图和鼠标键盘模拟，像人类一样在浏览器和各种软件间跳转解决问题。

五、 Anthropic 智能体落地三大核心原则

如果你决定开始构建 Agent，请务必严格遵守以下工程规范：

原则 1：保持极简设计 (Maintain Simplicity)

不要一开始就使用行业里那些庞大、复杂的 Agent 自动化框架。从最简单的 Prompt Chaining 或最基础的单 Agent 开始。系统越复杂，越难进行回归测试和确定性 Debug。只有当你能证明简单架构无法 cover 业务时，才允许增加架构复杂度。

原则 2：保证高度的透明度 (Prioritize Transparency)

必须在系统后台或前端，显式地记录和展示 Agent 的每一个思考步骤（Thought）和工具调用流（Action）。

  • 这不仅是为了让用户建立信任感，更重要的是为了让工程师能看清它是从哪一步开始”想歪的”，从而进行 Prompt 调优。

原则 3：精心雕琢你的 ACI (Agent-Computer Interface)

以前我们为人类写 API 接口和文档（API）；现在我们必须为 Agent 编写专门的计算机接口（ACI - Agent-Computer Interface）。

  • 换位思考： 站在模型的视角看，这个工具的名称和描述是否足够傻瓜、直观？
  • 防呆设计（Poka-yoke）： 改变工具的入参格式，尽量消除歧义。如果一个工具极其容易被大模型填错参数，不要指望靠优化 Prompt 解决，直接用代码重构这个工具的入参结构。
  • 提供详尽示例： 在工具的 JSON Schema 说明里，塞入真实的入参和边界情况（Edge cases）示例。

六、 总结建议

构建有效的智能体，其本质并不是追求让大模型变得多么”无所不能”，而是一个精密的工程学问题。

  1. 从单点起步： 绝大多数业务场景，用一个单用途（Single-purpose）的增强型 LLM 或硬编码工作流就能解决。
  2. 测试驱动： 为你的 Agent 建立一套全面的、包含数十个边界案例的评测集（Evaluations）。没有定量评测，优化 Agent 就是盲人摸象。
  3. 拥抱模块化： 确保你的系统是模块化的。当明年的大模型推理能力更强、速度更快、Token 更便宜时，你的系统架构应该能够通过直接”热插拔”更换底层模型来完成升级，而不是推倒重来。

OpenAI 推出的这篇 34 页白皮书报告 《A Practical Guide to Building AI Agents》（构建 AI 智能体实用指南），是专门针对企业级产品和工程团队的落地沉淀。它与 Anthropic 的视角相辅相成，但更侧重于生产环境的安全性、评估体系（Evals）以及单/多智能体编排的折中选择。

文／OpenAI 团队

随着大语言模型（LLM）在推理、多模态和工具调用能力上的突破，企业正从”自动化工作流”转向”自主智能体（Agents）”。本文结合了 OpenAI 在大量客户工程落地中的真实案例，旨在为产品与工程团队提供一份去伪存真的实操指南。

一、 什么是 Agent（智能体）？

在传统软件中，用户需要手动或通过死板的程序去串联工作流。而 Agent 是一种能够代表用户，以高度独立性（Independence）自主完成多步骤任务的系统。

  • 基本特征： 1. 独立性： 无需人类在每一步进行确认。

    \2. 多步骤流转： 比如”读取投诉 $\rightarrow$ 检索历史订单 $\rightarrow$ 判定是否合规 $\rightarrow$ 调用 API 自动退款”。

    \3. 自我纠错（Self-Correction）： 当 API 调用失败或捕获到异常时，它能自适应地调整策略并重试。

二、 智能体的三大基石 (Core Components)

OpenAI 认为，任何一个 Agent 都可以被拆解为最底层的三个核心组件：

$$\text{Agent} = \text{Model（模型）} + \text{Tools（工具）} + \text{Instructions（指令/护栏）}$$

  1. Model（模型核心）： 负责推理、意图分类和决策的大脑。
  2. Tools（工具箱）： 外部函数、API、数据库或软件接口（如执行 Python 代码、查询 CRM 账单）。
  3. Instructions（显式指引）： 为 Agent 划定的系统级 Prompt 和行为守则（Guardrails）。

三、 模型选择的工程学三大原则

不要在项目一开始就盲目追求低成本而使用弱模型。OpenAI 推荐的演进路径是：

  • 原则 1：通过评测建立基线（Set up Evals）。 必须先建立测试集，拒绝”凭感觉调优（Vibe Coding）”。
  • 原则 2：用最强模型压阵（Top-Down 策略）。 在原型阶段，无脑选用当前最强的旗舰模型（如 GPT-4o / 具备深度推理的推理模型）。先确保在最优大脑下任务能够跑通，触及正确率目标。
  • 原则 3：向下渐进式优化。 当准确率达标后，再尝试将某些子任务（如简单的意图分类、文本检索）热替换为体积更小、速度更快、成本更低的小模型（如 Mini / Nano 系列），从而优化延迟与 Token 账单。

四、 智能体编排模式 (Orchestration Patterns)

OpenAI 将常见的架构编排归纳为两大类，并给出了具体的适用图景：

  1. 单智能体系统 (Single-Agent Systems)

一个模型配备一组工具。所有的决策、反思、工具调用都发生在这一个模型的上下文循环中。

  • 优势： 架构极简，状态管理简单，Token 传输损耗低。
  • 劣势： 当工具过多时，模型会遭遇”上下文污染”或”工具混淆”。
  1. 多智能体系统 (Multi-Agent Systems)

当任务复杂度高、角色边界明显时，需要引入多智能体协作。OpenAI 指出，多智能体主要有两种流派：

  • 管理者模式 (Manager Pattern)：

    由一个”主 Agent（Manager）”坐镇中央，负责理解用户目标、拆解任务，然后像派发工单一样，把子任务分发给专门的下游 Agent（如翻译 Agent、合规审计 Agent），最后由 Manager 汇总结果。

    • 适用场景： 结构化、层级严密的企业级 B2B 业务流。

  • 去中心化模式 (Decentralized Pattern)：

    没有绝对的领导者，Agent 之间通过共享的上下文、特定的协议或消息总线进行动态路由和交接（例如：技术客服 Agent 解决不了问题，直接将上下文动态转交给高级 Debug Agent）。

    • 适用场景： 动态环境、边界模糊、需要高度弹性协同的场景（如客户支持体系）。

五、 工具与接口设计：ACI 的防错机制

Agent 能走多远，取决于它的工具好不好用。OpenAI 提出了以下工程铁律：

  • 严禁工具过载： 不要把几十个 API 塞给同一个 Agent，模型会在选择工具时变得犹豫且极易出错。
  • 防呆设计（Poka-yoke）： 在代码层面对工具的入参进行强类型约束（如显式定义 Enum 枚举值、限制 JSON Schema 的结构）。如果模型经常传错参数，应该在代码层拆分 API，而不是指望靠修改系统提示词来教育它。
  • 沙箱隔离： 任何涉及执行代码（Code Execution）或写操作（Write/Delete）的工具，必须部署在严格受限的沙盒环境中。

六、 安全与生产护栏 (Guardrails)

让 Agent 走向生产环境，最大的挑战是”确定性”与”安全性”。OpenAI 提出了三层纵深防御：

  1. 输入防御： 在用户 Prompt 进入 Agent 之前，必须经过内容安全审查（Content Safety System）以及提示词注入攻击（Prompt Injection）检测。
  2. 运行中防御（Human-in-the-Loop）： 对于高危动作（如批准大额退款、向客户发送最终邮件、删除数据），系统必须挂起并引入人类确认机制。Agent 只有建议权，没有最终执行权。
  3. 增量演进： 护栏的设计不该是一刀切的。应该根据真实的线上 Edge Cases（边缘案例）和失败日志，像编写单元测试一样，不断增补和迭代你的安全边界。

总结

OpenAI 的核心劝诫是：不要一开始就试图构建一个全知全能、复杂无比的完全自主多智能体系统。 企业落地最稳健的路径是：从单智能体（Single-Agent）起步 $\rightarrow$ 建立严密的定量评估（Evals） $\rightarrow$ 验证业务价值 $\rightarrow$ 逐步在痛点处引入多智能体分工或人类协同（Human-in-the-loop）。 稳扎稳打，让智能体像传统软件一样具备可预测性。

场景题：我要做一个高考志愿填报系统，面试官问我为什么我要选择agent而不是普通 workflow

这道面试题非常经典，面试官表面上在问”为什么用 Agent”，实际在考查你对复杂业务场景的架构选型能力、对大模型边界的认知，以及是否具备防范”技术自嗨”的工程思维。

如果你直接回答”因为 Agent 比较高级/聪明”，面试直接挂掉。你需要从高考志愿填报（尤其是中国高考填报）的底层业务痛点出发，给出降维打击的回答。

以下为你梳理的”满分面试话术”与架构拆解：

核心切入点：高考志愿填报的本质是什么？

中国的高考志愿填报不是一个简单的”根据分数查学校”的过程，它的本质是：在极度不透明、规则极度复杂（各省批次、新高考选科限制、位次换算）、且充满博弈和动态权衡的非线性决策过程。

核心理由 1：输入目标的”模糊性”与”多维度权衡”

  • Workflow 的死穴： 工作流需要结构化、确定性的输入。如果用户输入”考了 600 分，想学计算机，想去南方，就业要好，但也想冲一下 985”，传统工作流必须逼迫用户把这些期望硬编码成固定的过滤条件（如：省份=广东/浙江/江苏，专业=CS，学校类型=985）。一旦条件冲突，工作流直接返回空结果。
  • Agent 的优势（Think 能力）： Agent 能够理解模糊、口语化甚至互相矛盾的人类目标。它会把目标转化为多个相互制约的”权重因子”，在内部进行多轮逻辑推理（CoT）：”用户既想冲985，又想稳保计算机就业。根据往年数据，这两者在600分这个位次是冲突的。我应该优先生成两个方案：方案 A 牺牲学校冲专业，方案 B 牺牲专业冲学校，并主动向用户解释利弊。”

核心理由 2：规则与政策的”高动态性”与”非线性决策”

  • Workflow 的死穴： 工作流的路径是死板的（图结构 DAG）。高考志愿填报要考虑：新高考改制、高校当年招生计划变动、某专业今年突然爆冷或暴热。如果用 Workflow，你需要写无数个极其复杂的 if-else 分支，只要政策微调，整个工作流代码全部得重构，维护成本是灾难性的。
  • Agent 的优势（Observe 机制）： Agent 具备 工具调用（Tools） 和 自适应修正 能力。
    • 第一步：Agent 先调 API 查出 600 分能上的基础学校列表（Act）；
    • 第二步：它观察（Observe）到今年 A 大学在用户所在省份减少了 50 个计算机招生名额；
    • 第三步：它的大脑（Think）会立刻修正策略：”名额大减意味着往年投档线失去参考价值，今年分流可能会爆高，此校不能作为’稳妥’志愿，必须降级为’冲刺’志愿，并自动补选一台 B 大学作为兜底。”
    • 这种”走一步、看一步、调一步”的动态博弈，是静态工作流根本无法实现的。

核心理由 3：交互体验从”填表单”升级为”顾问式引导”

  • Workflow 的死穴： 用户必须在一开始就填好所有表单（输入所有参数），系统才能运行。这对于信息极度匮乏的高考生和家长来说，门槛极高。
  • Agent 的优势： 它可以实现 Human-in-the-Loop（人机协同）。Agent 在推进决策的过程中发现信息不足，会主动停下来反问用户：”我发现你的分数如果报华中科技大学的机械专业非常有把握，但你之前提到更想去大城市，你愿意为了去上海而接受一个普通一本的计算机专业吗？”这种启发式的多轮对话引导，能把家长的隐性需求一点点榨取出来。

💡 面试官一定会追问（杀招）：Agent 存在幻觉，如果报错、报滑档了，这个责任谁承担？你确定敢在高考这么严肃的场景用 Agent 吗？

这是面试官的连环陷阱！如果你一味吹捧 Agent 完美无瑕，就掉进去了。此时你需要展现出极其冷静的工程克制。

满分抗辩回答（架构演进）：

“面试官您说得非常对。在实际工程落地中，我绝对不会构建一个完全自主、放任不管的纯 Agent。高考志愿容错率为零，因此我的架构设计是 Agent + Workflow 混合双驱模式：”

  1. 意图生成与策略规划交给 Agent： 利用大模型的泛化能力，理解用户的诉求（想离家近、看重就业、保考研率等），动态匹配出几套合理的”冲、稳、保”策略梯度。
  2. 底层核心校验坚决回退到传统代码与 Workflow： Agent 生成的每一所学校、每一个专业志愿代码，必须灌入一个用传统 Go/Python 写的硬编码工作流（Workflow）进行像素级的规则校验。
    • 比如：校验用户的物理选科是否符合该校要求；
    • 校验志愿代码在当年的招生大册上是否存在；
    • 用数学公式严格计算滑档概率，一旦发现 Agent 激进冒进，Workflow 直接抛出异常阻断输出。

一句话总结结案：

“我选择 Agent，是为了解决用户’输入模糊、需求多变、决策博弈’的上限问题；而我结合传统工作流（Workflow），是为了死死守住’不滑档、数据精准、完全合规’的下限问题。两者不是非此即彼，而是前台 Agent 探路，后台 Workflow 筑墙。”

这个回答一出，面试官基本就能确定：你不仅懂最新的 AI 技术，更具备极其成熟的系统架构师思维。
